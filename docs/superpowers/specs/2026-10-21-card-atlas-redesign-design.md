# Card Atlas redesign: design

Date: 2026-10-21. Status: approved by the user 2026-10-21 (answers below).

## Intent

The current app (`web/`) is a single search page. It looks tidy but hides what the project produces: you cannot see why a card is a neighbour, the first screen is a headline, and nothing explains the model or its results. The user wants a site to put on a CV, finished tonight. It must make sense to someone who gives it 30 seconds and hold up for a technical reader who digs in. The user chose all four directions from the brainstorm, on two or three pages: the case study with a before-and-after comparison (A + D) on one page, and the Scryfall-like tool with the card map (B + C) on its own page or pages.

## Goals

1. **Case study page (`/how-it-works`), A + D.** Reads top to bottom as a project write-up:
   - Hero: one-line pitch ("Find Magic cards by what they do, not what they say"), a search box and example cards that jump into the explorer.
   - The problem: keyword search matches words; the example shows a lexical twin that does the opposite (Ghosts of the Innocent vs Furnace of Rath).
   - The approach: data (Scryfall cards, Scryfall Tagger tags as labels, family-grouped splits, sealed test set), training (contrastive fine-tuning of e5-base-v2 on tag-sharing pairs with lexical hard negatives), shown as a small diagram.
   - **Before and after (D)**: for a showcase card (or any card the reader types), two columns side by side, the pretrained model's top neighbours and the fine-tuned model's, each row with name and rules text.
   - Results: charts of dev nDCG@10 (full and hard-lexical) for the lexical baseline, pretrained E5, pretrained BGE, fine-tuned BGE and fine-tuned E5 (seed spread shown); the promotion test's bounds; the one-time sealed test; the trap exam; 2000 vs 4000 updates.
   - Limits, stated plainly: tag labels are a proxy; Deflecting Swat as the worked failure (its labels favour the wrong neighbour); T021.
   - Footer: repository link, write-up link, data attribution.
2. **Explorer page (`/`, the default), B + C.** One tool page with two linked views:
   - **Map**: every card as a dot on a 2D projection of the deployed model's vectors, coloured by colour identity, regions labelled by their most characteristic tag; pan and zoom; click a dot to select a card; the selected card and its neighbours are highlighted.
   - **Results**: the selected card (image, rules text, tags) and its neighbours as cards showing image, rules text and score. Each neighbour can open a side-by-side compare, with lines that appear on both cards highlighted.
   - The card's ability lines are clickable ("similar by this line"); filters (colour, mana value, type) sit in one collapsible row.
   - The URL holds the state (card, ability, filters), so links can be shared.
3. **Good design and fast.** The case study is prerendered HTML and loads no card data until the reader asks for it. The explorer loads data shards on demand, as now. Targets: Lighthouse performance ≥ 95 on `/how-it-works`, no layout shift, works at 360 px wide, keyboard-usable, light and dark themes.

## Non-goals

- No backend and no query-time model; everything is static files.
- No new training, labels or metrics for the site.
- No accounts, analytics, tracking or third-party scripts.
- No publication. The build is local; putting it online is a separate gate for the user.

## Anti-goals (a failure even if it works)

- Any number on the site that is not read from a run or evaluation record. Numbers come from a generated `site-metrics.json` built by a script from `runs/` records, never typed by hand.
- Overclaiming: proxy-tag results must be labelled as proxy results; the sealed test is described as one-time.
- A heavy page: chart or map libraries pulled in for what a few lines of SVG or canvas can do.

## Constraints

- Svelte stays (user). Stack: **SvelteKit with the static adapter** (my call: gives routing, prerendering of the case study and code splitting per page).
- Data: the existing release bundle schema v4 (cards, neighbours, abilities, lines, tags shards) stays the source for the explorer. New static files are added as a new site-data version, never by editing a finished release.
- Card images come from Scryfall's image CDN (as now); fonts are self-hosted.
- Python work runs on the CPU while x-2 trains on the GPU (one GPU training at a time).
- The deployed model may change tonight (confirm-x1-s1 if the promotion test passes). The site reads `current.json` and the generated metrics, so it follows whichever model is deployed.
- Disk: 38 GB free; the new data adds well under 1 GB.

## New data (generated by scripts, all from existing records)

- **Pretrained neighbours** for the before-and-after: encode the catalogue with pretrained e5-base-v2 on the CPU (same recipe: `query:` prefix, mean pooling, max length 94) and store each card's top-k in the same shard format. Only the neighbour shards are needed.
- **Map coordinates**: t-SNE (scikit-learn, already installed) of the deployed release's saved `vectors.npy`, stored as a compact binary (two int16 per card) in release card order; region labels from clustering the 2D points and taking each cluster's tag with the highest lift (minimum support), stored as JSON.
- **`site-metrics.json`**: the dev evaluation summaries, the promotion reports, the sealed report, the exam records, and the x-1 confirmation numbers, each with its source path.

## Left to the builder

- Exact layout, typography and colour palette, within: a calm editorial look for the case study, a dense tool look for the explorer, and one shared visual system.
- How regions are labelled on the map (number of clusters, lift threshold), as long as labels come from tags.
- Showcase cards for the before-and-after, chosen where both columns are readable and the difference is clear. One must be an honest mixed case.
- "Lines on both cards" means exact matches after number masking; the model's per-line evidence (ability neighbours) is used only where the bundle already has it.
